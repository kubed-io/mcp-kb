# kubed-mcp 0.8: One Listing per Via, the Cold-Start Fix and Pyroscope Source Links — Design

> **History.** Proposed for #126 (PR #127, into `main`). The draft was #126's notes in
> `.issue/issues.md`, with Dr K's rulings of 2026-11-28 (06:15). That brief was approved. The
> branch had no draft spec file. This file replaces the notes as the design of record. It was
> checked against `main`'s head and against quick-mcp's `v0.8.0` source (`delivery.py`,
> `_config.py`, `pyroscope.py`, `telemetry.py`, `CHANGELOG.md`). Its plan is
> [2026-11-28-kubed-mcp-0.8.md](2026-11-28-kubed-mcp-0.8.md). What it proposes goes into `specs/`
> in this pull request, and each row becomes true once the plan's tasks land.

## What changes

kb moves from `kubed-mcp>=0.6.1,<0.7` to `>=0.8.0,<0.9`. Three upstream releases reach kb:

1. **0.7.0 (quick-mcp#80): listings follow Via (DLV-9).** It was breaking upstream, but
   `skills/list` is unreleased here.

   | Via | `prompts/list` | `skills/list` | `agents/list` | `resources/list` default (`Listed`) |
   |---|---|---|---|---|
   | `mcp` (default) | the plugins' and the server's own | no skill of the plugins' | the plugins' | `skills` |
   | `extension` | the plugins' and the server's own | the plugins', up to the max | the plugins' | none |
   | `local` | the server's own only | none of the plugins' | none of the plugins' | none |

2. **0.7.1 (quick-mcp#99):** a cold pod's builds yield to the event loop and run one at a time,
   so `/health` and `server/discover` keep answering while the first clients' builds run.
3. **0.8.0 (quick-mcp#100):**
   - Profiles carry `service_repository` and `service_git_ref` from `SERVICE_REPOSITORY` and
     `SERVICE_GIT_REF`.
   - `python -m kubed.mcp.pyroscope` writes and checks `.pyroscope.yaml`.

kb writes code for one thing only: INS-11 under the default Via (D4). The rest is pins, tests,
the image and the record.

## Checked against the code and upstream

- **The pin** appears once, at `pyproject.toml:37`. Its comment is lines 28-36.
  `tests/test_packaging.py:164-179` holds the range. Both extras name `kubed-mcp[telemetry]` with
  no version.
- **How Via is resolved** (`delivery.py`). The first valid value wins, in this order:
  1. the `Kb-Via` header;
  2. `X-MCP-Via`;
  3. `?via=`;
  4. `delivery_default` (kb defines none);
  5. the config's `delivery.via`;
  6. the known-client table, which sets no Via;
  7. `mcp`.

  A declared extension is not a level, and neither is `_meta`. An in-memory `fastmcp.Client`
  sends no header, so an in-memory test can reach `extension` only through the config's
  `delivery.via` (D2).
- **`load_config`** (`_config.py`) takes `config=` as a mapping, one section or a list of
  sections, and never together with `argv=` or `environ=`. `DeliverySettings` is exported from
  `kubed.mcp`. So `load_config(sections=SECTIONS, config=[root, DeliverySettings(via="extension")])`
  is a load whose `.config` a `KnowledgeBase` can be built from. `create_app` requires
  `loaded.config is knowledge_base.config`.
- **`build_instructions`** takes `skills_extension` (`catalogue/instructions.py:91`) and uses it
  once (line 113). `ScopedInstructions` passes it (`mcp/instructions.py:70`) and is the module's
  only user of `EXTENSION_ID`. `EXTENSION_ID` stays in `mcp/request.py`, because tests import it.
  `extensions` is the only declaration kb reads.
- **The empty ref.** `telemetry.py::_profile_tags` adds a label only
  `if value := os.environ.get(variable)`, so an empty `SERVICE_GIT_REF` is no label. Configured
  `tags` are applied last and win.
- **The `.pyroscope.yaml` CLI.**
  - The forms are `--write <dist>` and `--check <dist> [file|-]`. The distribution argument is
    required for both.
  - `--check` reads stdin by default. It exits 0 when the file matches, 1 when it is stale (with a
    unified diff on stdout), and 2 for any other failure: empty input, an unreadable file, an
    unmappable image or a usage error.
  - The output starts with two comment lines. The first is
    ``# Generated by `python -m kubed.mcp.pyroscope --write kubed-mcp-kb` inside the server's image.``
  - The command needs the image's own paths (`/opt/venv/lib/python3.14/…`). A host checkout cannot
    produce or check the file.
- **The image.** The Dockerfile's `runner` stage ends `… EXPOSE 8000`, `USER 65534`,
  `ENTRYPOINT ["mcp-kb"]`, and it has no `RUN` after the cache-directory `mkdir`.
  `docker-compose.yaml` is the bake file, and its `build.args` holds `PY_VERSION` and
  `DEPS_FRESH`. `GIT_SHA` is already used as a tag (`kubed/mcp-kb:${GIT_SHA:-latest}`).
  `image.yml`'s push `paths` do not include `.pyroscope.yaml`.
- **The spec rule** ([specs/README.md](../specs/README.md)): a removed requirement leaves a gap,
  and its number is never reused. **HTTP-49 is free.**

## Decisions

- **D1. The pin is `"kubed-mcp>=0.8.0,<0.9",`.** The comment names, in order: the floor's 0.8.0
  source labels and `.pyroscope.yaml`; 0.7.1's cold start; 0.7.0's one listing per Via; and the
  ceiling, which stops short of 0.9. The 0.5.2 "never lower" note stays. The packaging test
  asserts a floor of at least `(0, 8, 0)` and at least `(0, 5, 2)`, and a ceiling of `(0, 9)`.
- **D2. One way to ask for `extension` per transport.**
  - **In memory:** `tests/conftest.py::extension_kb(config, cache)` loads `config` with
    `DeliverySettings(via="extension")`, builds the `KnowledgeBase` from `loaded.config`, and
    registers its app in `_APPS`. Every later `server_of(kb)` then returns that app.
  - **Over HTTP:** the header `VIA_EXTENSION = {"Kb-Via": "extension"}`, also in `conftest.py`,
    the way a real client asks.

  A test whose subject is the extension's listing (`skills/list`) moves onto one of the two. A test
  about the default keeps the default. A test that asserts both a `skills/list` listing and the
  default `resources/list` rows in one client is split in two. No call site gets a third way.
- **D3. The DLV-9 table is pinned as kb serves it.** One test per kind, in the tests that already
  pin Via:
  - `skills/list` by Via, over the synthetic tree;
  - `prompts/list`: only `local` drops the plugins' prompts;
  - `agents/list`: unchanged.

  The SKL-64 cap tests read `skills/list` under `extension` and the resource rows under the
  default.
- **D4. INS-11 under the default Via** (Dr K's ruling). Under `mcp`, every client gets the names,
  whether or not it declared the Skills extension. Under `extension` the names stay out, because
  `skills/list` carries them there.
  - `build_instructions` loses `skills_extension`.
  - `ScopedInstructions` stops passing it and drops the `EXTENSION_ID` import.
  - INS-3 is removed, and its number stays unused.
  - INS-2 says a declaration changes nothing in the text.
- **D5. Source labels, last in the final stage** (Dr K: "at the end of the final stage").
  - `ARG GIT_SHA`, then
    `ENV SERVICE_REPOSITORY=https://github.com/kubed-io/mcp-kb SERVICE_GIT_REF=${GIT_SHA}`.
  - These go after `USER 65534` and immediately before `ENTRYPOINT`.
  - The brief put them before `USER`. Below the `mkdir` `RUN`, both positions are metadata-only.
    "Last" is the stronger rule: an `ARG` takes part in the cache key of every `RUN` below it. So a
    test holds that no `RUN` follows `ARG GIT_SHA`, and a later `RUN` cannot be added below it
    unnoticed.
  - `docker-compose.yaml`'s `build.args` gains `GIT_SHA: ${GIT_SHA:-}`. The fallback is empty,
    never `latest`: `latest` is no git ref, so it would link every frame to a page that does not
    exist. An empty ref is no label.
- **D6. `.pyroscope.yaml` is generated, never hand-written.**
  - The committed file is exactly the output of
    `docker run --rm --entrypoint python <image> -m kubed.mcp.pyroscope --write kubed-mcp-kb`,
    run in an amd64 image built from this branch. That includes upstream's two-line header.
  - The suite checks only that the header names `--write kubed-mcp-kb`. A test that compared the
    file to the installed kubed-mcp would turn `main` red on an upstream patch release, which is
    what Dr K ruled the check must not do.
- **D7. The CI check warns and never fails** (Dr K's ruling). It runs on pushed builds only. Exit 1
  is a `::warning::` with the diff in the step summary. Exit 2 and a failed pull are a warning with
  an empty diff. The step always passes. The App cannot edit `.github/`, so the step is written out
  in the plan for Dr K to add by hand. The block also adds `.pyroscope.yaml` to `image.yml`'s push
  `paths`, so a commit that only regenerates the file is checked.
- **D8. The live cap check reads the default listing.** `tests/live/test_live_cap.py` takes the
  listed set from the `SKILL.md` rows of `resources/list`, not from `skills/list`, which is empty
  under `mcp`. So it checks INS-24's count against what a default client is shown.
- **D9. The changelog** edits `[Unreleased]` only, with no BREAKING line (ruled). Its exact lines
  are in the plan.

## Requirement text

These are the new and changed rows as they go into `specs/`. IDs are stable. The only new one is
HTTP-49. INS-3 is removed.

### scoping-and-instructions.md

- **INS-2:** "The text is built from the current catalogue, the request's scope, whether the client
  reads resources, which is kubed-mcp's resolved `resources` setting for the request (DLV-2,
  DLV-15; see [http-and-tools.md](http-and-tools.md)), its resolved `via`, and the request's
  resource prefix, which is INS-16's. Whether the client declared an extension changes nothing in
  it."
- **INS-3:** removed, along with its paragraph. The number is not reused.
- **INS-11:** "The pointer also lists skill names when all of these hold: the request's Via is `mcp`
  (INS-20), exactly one library is selected, and that library's `listSkills` is true. A client that
  declared the Skills extension gets them too. It then reads
  `Skills (skill://<library>/_index.md): <names>`."
- **INS-19, third bullet:** "The lines are written under `mcp` and `extension` (INS-20), and in the
  INS-11 form. INS-6 still decides which libraries have a section."

### skills.md

- **SKL-62:** "Under Via `extension`, `skills/list` lists the in-scope skills up to the request's max
  (SKL-64). Under `mcp` and `local` it lists no skill, and `skills/get` still serves each one in
  scope (DLV-9, DLV-10). Under `mcp` the skills are listed as `resources/list` rows instead
  (SKL-14). `Listed` does not change it. kb adds no filter of its own. Under `local` none is listed
  and none counts as cut."

### prompts.md

- **PRM-64:** "Under Via `local`, `prompts/list` lists no plugin prompt, and `prompts/get` still
  serves one (DLV-9). Under `mcp` and `extension` it lists them all. kb adds no filter of its own."

### config-and-sources.md

- **CFG-15:** after "…carry the service name `OTEL_SERVICE_NAME`, else `mcp-kb`.", add: "Profiles
  from the image also carry `service_repository` and `service_git_ref` (HTTP-49), unless `tags`
  sets either one, because `tags` wins. The repository's `.pyroscope.yaml` maps each frame's file to
  its source at those labels: kb's own in this repository, and kubed-mcp, FastMCP and the standard
  library on GitHub at the versions the image installs."

### http-and-tools.md

- **HTTP-49 (new, after HTTP-43):** "The image sets `SERVICE_REPOSITORY=https://github.com/kubed-io/mcp-kb`
  and `SERVICE_GIT_REF` to the commit it was built from. A build given no commit sets
  `SERVICE_GIT_REF` empty, which is no label. Both are set after the image's last `RUN`."

## Not part of this change
