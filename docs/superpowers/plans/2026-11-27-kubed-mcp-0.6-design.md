## What changes

kb moves to kubed-mcp 0.6 (quick-mcp Epic 6, quick-mcp#83). Three upstream changes reach kb:

1. **SEP-2640 final (quick-mcp#79).** `resources/directory/read` results carry
   `resultType: "complete"`. A skill's `_manifest`, and the `_index.md` and `_index.json` beside
   each directory, are *views*: each reads at its exact URI and none is listed in an entry's
   `resources`.
2. **The listing cap (quick-mcp#81).** `skills/list`, and the skill rows of `resources/list` and
   the `list_resources` tool, list at most 100 skills by default. The cap is set per request with
   `Kb-Max`, `X-MCP-Max` or `?max=`, and per server with `delivery.max` (`DELIVERY_MAX`,
   `--delivery-max`). `all` means no cap. The handshake hands the instructions hook a count of
   what was listed and what was cut.
3. **Shutdown (quick-mcp#54).** Open `subscriptions/listen` streams end cleanly on a stop, and
   in-flight calls get `serving.graceful_timeout` seconds (`GRACEFUL_TIMEOUT`,
   `--graceful-timeout`, 15 by default).

kb writes code for two things only: the INS-21 footer and INS-24's cut line. Everything else is
pins, tests and the record.

## Upstream, as read on quick-mcp's `v0.6.0-rc.4`

- `kubed/mcp/delivery.py`: `Resolved` has `max: int | None = 100` (None is no cap) and
  `skills: SkillCount | None = None`. `SkillCount` is `listed: int, cut: int`. The max is read
  from `<Prefix>-Max`, then `X-MCP-Max`, then `?max=`, then `delivery.max`. `all` (any case) is
  no cap. A value that is not a whole number of 1 or more is ignored with one warning, and the
  next level answers. With nothing set, it is 100.
- `kubed/mcp/plugins.py`: skills are listed in build order: plugins in the order added, and in
  each plugin the skill folders as found, each folder's skills in name order. The cap keeps the
  first `room` skills and counts the rest as cut. It applies to `skills/list` and to the skill
  rows of `resources/list`. Reads, `skills/get` and the indexes are not cut. Under `local` the
  plugins' skills are unlisted, and none counts as cut.

## Decisions

- **D1. The pin is `kubed-mcp>=0.6.0,<0.7`.** Dr K's ruling of 13:42, which replaced ruling A1's
  rc2, set the floor at rc4 and had it move with each rc and then to the final. 0.6.0 shipped on
  2026-11-27 at 15:29, so the floor is the final. It is rc4 with nothing added that kb uses. rc4
  contains rc2's cap and SEP-2640 work. It also brings rc3's `-32603` for a failed view or build
  (quick-mcp#90) and rc4's async views (quick-mcp#86). Neither needs kb code: `view()` does not
  raise by design, and no test pins the old code 0.
- **D2. Shutdown needs no kb code.** `serving.graceful_timeout` is upstream's item on kb's
  `Serving`. The schema, `wiki/Configuration.md`, `config.py`'s docstring table and CFG-1's table
  gain the row, and HTTP-48 states the behaviour. The wiki's Kubernetes section says to keep
  `terminationGracePeriodSeconds` above 15 s.
- **D3. The `extension` footer drops the `_manifest`** (ruling A3, INS-21). It becomes exactly
  `Skills arrive through the Skills extension; each reads at skill://<library>/<path>/SKILL.md, and its entry lists the files it ships.`
  INS-15's `mcp` footer keeps its `_manifest` clause. kb's own indexes (SKL-18) still name the
  `_manifest`: they are read through `resources/read`, not from inside a skill.
- **D4. Views are in no entry** (SKL-24, SKL-46, SKL-56, SKL-57). This is upstream's behaviour,
  pinned by a test. **SKL-63** records what is already true: kb's rewriter never writes a view's
  address into a skill's file. A qualified name becomes a `SKILL.md` address (SKL-55), and a
  placeholder becomes a library, a skill's directory or a path below one (SKL-25, SKL-52).
- **D5. The plugin-root fallback is a `resources/read` feature** (ruling A4, SKL-30, SKL-33). Its
  file is in no entry, so a host that verifies a skill's files against its entry refuses it.
  It serves Via `mcp` clients. There is no workaround and no upstream ask in this pull request
  (the parent's open question 3).
- **D6. `resultType` on every directory read** (ruling A8, SKL-51). A test pins it on a skill's
  root, a library and a folder. The library and folder answers are built from
  `CatalogueProvider.children`. If upstream leaves `resultType` off those, the two cases are
  `xfail(strict=True)` with the reason
  `kubed-mcp adds no resultType to a provider's directory answer (quick-mcp; reported to #112)`,
  and the pull request reports it to #112. kb adds no wrapper.
- **D7. The cap is kubed-mcp's, and kb sets no default** (ruling A5). The SCP-2 row is
  `| Max | Kb-Max | max | X-MCP-Max | — |`. SKL-14, SKL-48 and SKL-62 say the listing is capped and
  what a cut skill still does. **SKL-64** restates upstream's order as kb's config produces it
  (ruling A6). HTTP-42's echo gains `max`.
- **D8. `_files.md` rows are never cut.** They are kb's resources, not the plugin layer's skill
  rows. A test holds it under `Kb-Max: 1`.
- **D9. INS-24, the cut line** (ruling A7). When `Resolved.skills` is set and its `cut` is above
  0, under Via `mcp` and `extension`, the text gets one more paragraph, after the sections and
  before the footer:
  `<listed> of <listed + cut> skills are listed; every skill reads through its library's _index.md.`
  - No line when `skills` is None. Upstream fills it only on `initialize` and `server/discover`.
  - No line when `cut` is 0.
  - Never under `local`, and never in INS-23's failure footer.
  - `build_instructions` takes the count as `skills: tuple[int, int] | None` (listed, cut): plain
    ints, so `catalogue/` imports no kubed-mcp type. `ScopedInstructions` passes
    `(delivery.skills.listed, delivery.skills.cut)`, or None.
  - `_index.md` in the line is a word, not an address, so the prefix (INS-16) changes nothing in
    it.
- **D10. Naming the skills past 100 on the unscoped route** (ruling A6, as Dr K defined it at
  13:42). The deployment's config is not in this repository, and hard-coded names would go stale
  the first time it changes. So the test names the cut skills from the route itself:
  - The in-repo suite pins the rule, with names, on the synthetic tree (D7).
  - `tests/live/test_live_cap.py` derives the cut on the running kb's unscoped route:
    1. The listed set is the default `skills/list`.
    2. The indexed set is every `SKILL.md` that the libraries' `_index.md` files reach. The walk
       starts at each library's `_index.md` (the libraries are `/health`'s `libraries`), follows
       each folder line to that folder's `_index.md`, and collects each skill line.
    3. The cut is the indexed set minus the listed set.
  - It asserts:
    - the listed set is inside the indexed set;
    - the listing holds exactly `min(100, total)` skills;
    - the handshake's count matches: the instructions carry INS-24's line with `listed` and
      `total` when the cut is not empty, and no such line when it is;
    - every cut skill answers `skills/get`, its `SKILL.md` reads, and its line is in the
      `_index.md` of the directory it sits in (its library's, or its folder's below it).
  - No name is written into the test. What the first live run on the deployment finds cut goes in
    the pull request's report. The prediction, not checked against the deployed config, is that
    `skill://svelte/svelte-core-bestpractices/SKILL.md` alone is cut, if `svelte` is the last
    library and the route serves 101.
- **D11. The split** (ruling A2). This pull request does not cover the following, which go to the
  follow-up sub-issue the parent files when quick-mcp#80 ships. 0.6.0 shipped without it, so the
  final pin landed here (D1):
  - #80's per-client delivery defaults;
  - the mode × kind cells (which agents each Via gets, and from where);
  - the Via re-check for the clients kb's tests use.

  The spec states the split here and nowhere in `specs/`, which hold statements only.
