# kubed-mcp 0.3 Pin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use skill://superpowers/subagent-driven-development/SKILL.md (recommended) or skill://superpowers/executing-plans/SKILL.md to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** kb runs on `kubed-mcp>=0.3.0,<0.4`. Nothing it serves changes except what kubed-mcp 0.2.0
and 0.3.0 add to every server: `_meta["io.kubed/delivery"]` on the handshake.

**Architecture:** One dependency line in `pyproject.toml`, then the whole suite on the new release.
kb registers its mirror tools with `mcp.tool` and adds no kubed-mcp plugin (`add_plugin` appears
only in a test, on a bare `QuickMCP`). So kubed-mcp's own `list_resources` and `read_resource`
tools never serve kb, and the 0.2 refusal of a plugin beside a server's own tools never fires.
Three new tests pin the places where kubed-mcp 0.2 and kb now read the same request.

**Tech Stack:** Python ≥3.11, `kubed-mcp` 0.3.0 (FastMCP through its facade), pytest +
pytest-asyncio, uvicorn for the HTTP tests.

**Spec:** this file's Design section (the change is too small for a design doc of its own), and
[HTTP-42](../specs/http-and-tools.md), added *(proposed)* with this plan. Starts from #92's
notes, adopts a release of kubed-io/quick-mcp#16, and carries Dr K's retarget from 0.2.0 to 0.3.0.

## Design

**The pin.** The branch is based on `issue-80`, where the line is `"kubed-mcp==0.2.0rc2"`
(`pyproject.toml:33`). It becomes `"kubed-mcp>=0.3.0,<0.4"`: an exact `==` is the form for release
candidates only. kb pins once, past rc3 and 0.2.0, so #78 (telemetry) builds on this pin with no pin
change of its own. It is the only kubed-mcp pin: `scripts/requirements.py` reads pyproject, and CI installs `.`,
`.[test]` and `.[test,build]`. Nothing installs from git.

**What 0.3.0 brings, and what reaches kb.** 0.3.0 is 0.2.0 plus telemetry. Telemetry is the
`[telemetry]` extra and loads lazily, so kb, which does not take the extra, sees no change from it.
What reaches kb from 0.2.0:

| kubed-mcp 0.2 | Reaches kb? |
|---|---|
| `_meta["io.kubed/delivery"]` on `initialize` and `server/discover` | **Yes**, on every handshake. HTTP-42 records it |
| Known clients: VS Code resolves `resources=off` with no header, so kubed-mcp lists its `list_resources` / `read_resource` | **Echo only.** Those are the plugin layer's tools, and kb has no plugin. kb's `HideMirrorTools` reads kb's own `X-MCP-Resources` / `?resources=`, so VS Code still sees no kb tool (TOOL-2). The named change moves to #86 |
| A plugin refused beside a server's own `list_resources` / `read_resource` | No, because kb adds no plugin |
| `X-MCP-Resource-Prefix` / `?prefix=` stripped from incoming addresses and written into served text | **Shared input.** kb reads the same two names (`PREFIX_ALIAS`, `PREFIX_PARAM`) and prefixes its own text. Task 2 proves the prefix is written once |
| `%2F` fails as missing, `.`/`..` resolved, plugin namespaces and `prompts://` / `agents://` | Plugin layer, or already true of kb (`ReadTheAddress`) |
| `header_prefix`, `X-MCP-Via`, `X-MCP-Listed`, `mcp.instructions`, `delivery_default` | Not used here. They come with #86 and #87 |

**The echo can disagree with kb, and that is accepted here.** kubed-mcp resolves delivery from its
own names, not kb's `Kb-` names, because kb does not pass `header_prefix`. Two cases follow. A
`Kb-Resource-Prefix` is not echoed. A VS Code client is echoed `resources: off` while kb lists it no
tool. Both end when #86 and #87 hand delivery to kubed-mcp. HTTP-42 states the disagreement, so the
spec does not claim the echo describes kb.

**Not in this change:** `header_prefix="Kb"`, any change to `mcp/request.py` or `HideMirrorTools`,
the `[telemetry]` extra, and kb's mirror tools giving way to kubed-mcp's.

## Global Constraints

- **Pin, verbatim:** `"kubed-mcp>=0.3.0,<0.4",`. Keep the comment above it. Its last sentence stays
  "Pre-1.0, so a minor is a break."
- **Toolchain, as CI runs it:** `pip install -e ".[test]"`, then `ruff check .` and `pytest` from
  the repository root (`test.yml`). Check out the `wiki/` submodule (`git submodule update --init`)
  so `tests/test_wiki.py` runs and does not skip. Package (`package.yml`): `python -m build` and
  `twine check --strict dist/*`. Dependency audit (`lint.yml`): `pip install -e .`,
  `pip freeze --exclude-editable > requirements.txt`, `pip-audit -r requirements.txt`.
- **Python 3.11 is the floor.** Lines are at most 88 columns. A pull request is tested on 3.11 and
  3.14.
- **Through the facade only:** `kubed.mcp`, `kubed.mcp.protocol`, `kubed.mcp.request`. Never import
  `fastmcp`, `mcp` or `mcp_types` in `kubed/`. Tests already import `fastmcp.Client`, which stays.
- **Do not weaken an existing assertion to make it pass on 0.3.** A test that fails for a reason
  other than the handshake's new `_meta` key is a finding: stop and report it with the output.
- **Markers:** an in-process test is `@pytest.mark.unit`, and a uvicorn one is
  `@pytest.mark.integration`.
- **Public repo:** the maintainer is Dr K; no names or real hostnames.
- **Commits** link kubed-io/quick-mcp#16 and end with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A prefix kubed-mcp also reads is written once.** With `X-MCP-Resource-Prefix: kb+` or
   `?prefix=kb%2B`, a client expects `kb+skill://` once in a body, the instructions and a prompt,
   never `kb+kb+`, and digests that still match the bytes read. → Task 2,
   `test_a_prefix_kubed_mcp_also_reads_is_written_once`.
2. **VS Code with no header sees what it saw before:** no tool in `tools/list`, and `read_resource`
   still callable by name (TOOL-5). → Task 2, `test_vs_code_sees_no_mirror_tool_without_a_header`.
3. **The handshake echo is there in both eras**, with the disagreement HTTP-42 states. → Task 2,
   `test_the_handshake_carries_the_delivery_echo`.
4. **`X-MCP-Resources: off` still lists kb's own `list_resources` and `read_resource`**, once each,
   and the server starts with no refusal. → existing `test_tools_mode_with_the_prefix`
   (`tests/test_addressing_http.py`) and `tests/test_scope_and_prompt_tools.py`, unchanged in Task 1.
5. **A whole-result comparison that meets the new `_meta` key** is fixed by leaving out that one
   key, never by dropping `_meta`. → Task 1, Step 3.

- [ ] **Step 1: Write the tests**

  In `tests/test_addressing_http.py`, `@pytest.mark.integration`, parametrized over the two ways
  kubed-mcp also reads a prefix:

```python
@pytest.mark.integration
@pytest.mark.parametrize(
    ("suffix", "headers"),
    [("", {"X-MCP-Resource-Prefix": "kb+"}), ("?prefix=kb%2B", {})],
    ids=["header", "param"],
)
async def test_a_prefix_kubed_mcp_also_reads_is_written_once(server_url, suffix, headers):
    url, headers = server_url + suffix, {**PIN, **headers}
    index = await read(url, "skill://flatsource/_index.md", headers)
    assert "kb+skill://flatsource/alpha/SKILL.md" in index
    body = await read(url, "kb+skill://flatsource/alpha/SKILL.md", headers)
    assert "See kb+skill://flatsource/beta/SKILL.md." in body
    async with _client(url, headers) as client:
        assert "kb+skill://" in client.instructions
        cited = await client.get_prompt("flatsource_cite")
    assert cited.messages[0].content.text == "Read kb+skill://flatsource/shared/x.md.\n"
    for text in (index, body, client.instructions):
        assert "kb+kb+" not in text
    got = await skills_request(
        url, "skills/get", headers, uri="skill://flatsource/alpha/SKILL.md"
    )
    for file in got["skill"]["resources"]:
        served = (await read(url, file["uri"], headers)).encode("utf-8")
        assert file["digest"] == f"sha256:{hashlib.sha256(served).hexdigest()}"
```

  In `tests/test_server.py`, both `@pytest.mark.unit`:
  - `test_vs_code_sees_no_mirror_tool_without_a_header(skills_dir)`: an in-process
    `Client(server_of(server), mode="legacy", client_info=<Implementation name="Visual Studio Code"
    version="1.99.0">)` with no header. Assert `await client.list_tools() == []`, and that
    `await call(client, "read_resource", uri="skill://flatsource/_index.md")` contains
    `skill://flatsource/alpha/SKILL.md`.
  - `test_the_handshake_carries_the_delivery_echo(skills_dir)`: in `legacy` mode,
    `DELIVERY_META in client.initialize_result.meta`. In `auto` mode,
    `DELIVERY_META in (await request(client, "server/discover"))["_meta"]`. Then, for the
    `Visual Studio Code` client of the test above, the echo's resources field reads `"off"`, which
    is the disagreement HTTP-42 states.

  Expected: PASS. These pin behaviour that should already hold after Task 1, so a failure is a
  finding, not a test to bend. What each failure means:

    `resources: "off"`, assert on the field that carries it, and say so in the commit body. If
    `auto` mode never reports a `clientInfo`, run the VS Code half in `legacy` only, and say so
    too.
